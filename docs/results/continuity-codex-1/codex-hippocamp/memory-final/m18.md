# Current state

- Checked out fix/late-dedupe with a clean working tree after the user reported corrected vendor_a orders losing deduplication again. Existing fix at 8126d66 addresses this; main remains unchanged for the upcoming release. Do not merge without further instruction.
- Shared dedupe on this branch retains the last file row per (vendor, order_id), regardless of timestamp, preserving keys' first-appearance order. It reads the full file before uploading, retains one normalized row per unique order, and hashes only winners. README and Unreleased changelog describe the behavior and memory tradeoff.
- Keep sequential uploads; multiprocessing was previously reverted because it broke ordering. Batches contain at most 2,000 rows, additionally split by exact encoded JSON size at 4,000,000 bytes. Oversized individual rows raise ValueError.
- Timestamp normalization uses a bounded 4,096-entry per-file cache and a fast path outside Paris clock transitions; DST gap/fold validation remains. Hash serialization reuses an encoder.
- vendor_a, vendor_b and vendor_c use the shared registry.
- Always run smoke with INGEST_FAKE_WAREHOUSE=1; without it the script posts to production.
- User confirmed vendor_a 2024–2025 history loaded on 2026-11-08. Complete; do not rerun.
