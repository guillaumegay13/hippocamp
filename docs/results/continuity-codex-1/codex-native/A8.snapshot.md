# Postgres retry queue deployment

- Provision durable Postgres storage and set `DATABASE_URL` (or standard `PG*`
  variables). The application role must be able to create tables, indexes, and
  add columns. Run `npm ci`, `npm test`, and `npm run build` before deployment.
- Drain the old in-memory workers before switching traffic; their pending work
  is not migrated to Postgres. Start the new service only after database setup
  succeeds. Startup creates `deliveries`, `delivery_attempts`, and the pending
  index, and adds `retry_delay_ms` with default `100` to existing deliveries.
- For a large existing table, build the new index before deploying, outside a
  transaction, to avoid a blocking index build at startup:

  ```sql
  CREATE INDEX CONCURRENTLY IF NOT EXISTS deliveries_pending_available_id_idx
    ON deliveries (available_at, id) WHERE status = 'pending';
  ```

  Verify the index build completed successfully before starting the new version.
  The old `deliveries_pending_idx` can then be dropped concurrently.
- Smoke-test a signed webhook: expect `202`, then check its admin status and
  attempt history. A target returning 5xx should retry up to five total attempts,
  with waits of 100, 200, 400, and 800 ms by default. Other responses and network
  errors are not retried. Optional source `retryDelayMs` changes only new jobs;
  it must be an integer from 0 to 268435455.
- Restart once with pending work and verify it resumes; interrupted jobs become
  claimable after the 60-second lease expires. Targets must deduplicate using
  `x-relay-delivery`, since retries and crash recovery can send duplicates.
- To roll back, stop intake and drain Postgres workers first. Keep the database
  and queued rows; an older in-memory version cannot resume them. Do not drop
  queue tables or columns during rollback.
