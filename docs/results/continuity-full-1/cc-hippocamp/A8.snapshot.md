# Deploy notes: retry queue moved from Redis to Postgres

Pending retries now live in the Postgres `deliveries` table. Redis is no longer used.

## Before deploying

- Give relay a Postgres database. Set `DATABASE_URL`, or the standard `PG*` env vars (`PGHOST`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, ...).
- The relay role needs `CREATE` on the schema for the first start. On startup relay runs `CREATE TABLE IF NOT EXISTS deliveries` and `CREATE INDEX IF NOT EXISTS deliveries_due_at_idx`. If the table is created ahead of time, keep that partial index on `due_at`. Without it, the claim query does a full scan.
- `REDIS_URL` is no longer read, so it can be removed.

## Deploying

- If Postgres is unreachable at startup, relay exits with `relay failed to start` instead of running without a queue.
- Retries still queued in Redis are not moved over automatically. They have to be backfilled into `deliveries` (prod: ops ran this backfill on 2026-11-04).
- Running several instances is safe. Workers claim rows with `FOR UPDATE SKIP LOCKED` and a 30s lease. Delivery is at-least-once: if an instance dies mid-attempt, the row becomes due again after the lease and is retried. Clients can deduplicate on the `x-relay-delivery` header.

## Rollback

- Older builds read retries from Redis only. Any retries still pending in `deliveries` will not be picked up after a rollback, so drain or copy them back first.

## Still not persistent

- Delivery records and attempt history (what the admin API shows) are still in memory and are lost on restart. Only pending retries survive.
