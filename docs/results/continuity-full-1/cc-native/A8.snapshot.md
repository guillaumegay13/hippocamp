# Deploy notes: Redis → Postgres retry queue

Retries no longer use Redis. They live in a Postgres `deliveries` table (`id`, `due_at` in epoch ms, `job` JSON), polled by a worker inside the server process.

## Before deploying

- Set `DATABASE_URL` on every relay instance. Without it the server falls back to `postgres://localhost:5432/relay`.
- The relay's DB user needs `CREATE` on the schema (only for the first start) plus `SELECT/INSERT/UPDATE/DELETE` on `deliveries`.
- Prod already has the `deliveries` table with rows backfilled from Redis (2026-11-04). Check that the index exists:
  ```sql
  SELECT indexname FROM pg_indexes WHERE tablename = 'deliveries';
  ```
  If `deliveries_due_at_idx` is missing, create it **before** deploying, without blocking writes:
  ```sql
  CREATE INDEX CONCURRENTLY IF NOT EXISTS deliveries_due_at_idx ON deliveries (due_at);
  ```
  Otherwise startup runs a plain `CREATE INDEX`, which locks the table for writes while it builds.

## Deploying

- On startup the server runs `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`. If that fails the process exits with `failed to create deliveries table`.
- Running several instances is safe: claims use `FOR UPDATE SKIP LOCKED`, and a claimed retry is hidden for 30 s (lease). If an instance dies mid-retry, another picks it up after the lease expires.
- Redis is no longer read. Anything still in Redis that wasn't backfilled will not be retried.

## After deploying

- Watch the logs for `retry worker:` errors.
- Pending retries: `SELECT count(*) FROM deliveries;`. Overdue ones: `SELECT count(*) FROM deliveries WHERE due_at < extract(epoch FROM now()) * 1000;`. That number should stay near zero.

## Rollback

Rolling back to the Redis build drops any retries queued in Postgres since the deploy. Drain the table first, or accept losing them.
